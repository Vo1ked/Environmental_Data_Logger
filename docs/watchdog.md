# WDT и panic

Курсовая использует Task Watchdog ESP-IDF. Дополнительная задача для кормления WDT не создаётся: зарегистрирован Manager, который проверяет независимые сроки работы модулей. Исходники: `main/watchdog/watchdog.c`, интеграция в `main/manager/manager.c`, `main/storage/flash_log.c`, `main/uart/uart_task.c` и `main/main.c`.

## Сроки и условия

| Канал | Когда начинается контроль | Срок | Что подтверждает работу |
| --- | --- | --- | --- |
| Manager / TWDT | До стартовых уведомлений задачам | 5 с без кормления TWDT | Проверка всех каналов без обнаруженных просрочек |
| Sensor | Перед отправкой SENSOR_SAMPLE или SENSOR_SET_TIME | 3 с | Manager получил ответ, в том числе с ошибкой устройства |
| Flash Writer | Перед любым запросом, включая FLASH_SCAN при старте | 5 с без прогресса | Обработанный сектор scan, успешная операция чтения/записи/стирания; окончательно — ответ Manager |
| Display | Перед отправкой снимка на OLED | 3 с | Manager получил ответ, в том числе с ошибкой OLED |
| UART | До запуска задач и перед отправкой resume | 3 с без выполнения цикла | Вернулся вызов обслуживания UART; наличие входящих байтов не требуется |
| Подготовка сна | Перед отправкой UART_PREPARE_SLEEP | 3 с | Manager получил EVENT_UART_PAUSED, успешный или с отказом |

Прикладные сроки определены в `main/app_config.h`, аппаратный таймаут TWDT — `CONFIG_ESP_TASK_WDT_TIMEOUT_S`. Это разные интервалы: при зависании Sensor сначала истекают 3 секунды на ответ, затем Manager перестаёт кормить TWDT, и ещё в пределах примерно 5 секунд бодрствования происходит panic/reset. Для Flash соответствующее суммарное время — примерно до 10 секунд от последнего прогресса. Если завис сам Manager, его контролирует непосредственно TWDT.

Сроки отсчитываются по монотонному `esp_timer`, поэтому команда установки RTC на них не влияет. Общие поля защищены короткими критическими секциями для двух ядер. Просрочка проверяется также при завершении, продлении и повторном открытии канала; позднее событие не может снять ошибку. Прогресс Flash не продлевает срок Sensor или другого канала.

Ожидание задачи в пустой очереди не контролируется как активная операция. Для обнаружения зависания после отправки задания контроль начинается **до** помещения запроса в очередь; при неудачной отправке снимается. Завершённый запрос с ошибкой BME280, RTC, OLED или flash не считается зависанием.

Manager ставит текст в очередь UART без ожидания свободного места: поток команд не должен задерживать обработку ответов рабочих задач. При переполнении выходной очереди часть диагностических строк/ответов может быть отброшена; запрос следует повторить после завершения текущего вывода. Flash по-прежнему ограниченно ждёт очередь при выводе `read` и возвращает ошибку, если передать запись не удалось.

После обнаружения просрочки Manager выводит `Deadline exceeded: <channel>` через системную консоль UART0, прекращает кормить TWDT и ждёт перезапуска, вызывая `vTaskDelay`. Idle-задачи остаются работоспособными. Новые задания и Light Sleep не запускаются; уже работающие задачи могут закончить принятые операции. Диагностика не зависит от очереди logger или прикладного UART1.

## Настройки panic

В `sdkconfig` и `sdkconfig.defaults` включены:

```text
CONFIG_ESP_TASK_WDT_EN=y
CONFIG_ESP_TASK_WDT_INIT=y
CONFIG_ESP_TASK_WDT_TIMEOUT_S=5
CONFIG_ESP_TASK_WDT_CHECK_IDLE_TASK_CPU0=y
CONFIG_ESP_TASK_WDT_CHECK_IDLE_TASK_CPU1=y
CONFIG_ESP_TASK_WDT_PANIC=y
CONFIG_ESP_SYSTEM_PANIC_PRINT_REBOOT=y
CONFIG_ESP_SYSTEM_PANIC_REBOOT_DELAY_SECONDS=0
```

При старте приложение использует `esp_task_wdt_reconfigure()` для автоматически инициализированного TWDT; если TWDT ещё не инициализирован, вызывает `esp_task_wdt_init()`. Устанавливается `trigger_panic=true` и контроль Idle-задач всех активных ядер, затем подписывается Manager. Ошибки настройки не игнорируются. Системный Interrupt WDT остаётся включённым.

Поведение TWDT и panic описано в [документации Espressif](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-reference/system/wdts.html). API также сверены с локальными заголовками установленного ESP-IDF 6.1.

## Light Sleep

До сна должны завершиться Sensor, Display и Flash, пройти logger_flush и подтверждение паузы UART. Ожидание этого подтверждения имеет отдельный срок. Только после положительного ответа UART его периодический контроль приостанавливается; перед отправкой resume запускается заново, включая отказ от сна или ошибку `esp_light_sleep_start()`.

Manager остаётся подписанным на TWDT. Приложение не отключает аппаратные watchdog перед сном; их обработкой на уровне периферии занимается ESP-IDF. Один сон ограничен `APP_MAX_SLEEP_MS=1000`, а статическая проверка требует запас относительно таймаута TWDT. Все активные операции завершаются до сна, поэтому время сна не расходует их программные сроки. Проверка повторных переходов сон/пробуждение на плате обязательна.

## Проверка на плате

Сборка, прошивка и аппаратные испытания выполняются пользователем. Следующие сценарии пока не запускались. Подготовить несколько сохранённых записей через `flush`; RAM-буфер при перезапуске теряется. Проверки WDT выполнять без OpenOCD/JTAG: отладчик может отключать watchdog.

1. **Штатная работа:** проверить `status` (WDT=ON, timeout=5 s, panic=ON), несколько минут измерений, отсутствие команд, Light Sleep и пробуждение по UART. Перезапусков быть не должно.
2. **Ошибки устройств:** запуск без BME280, RTC или OLED должен давать сообщения об ошибках, но не WDT reset, пока задачи возвращают ответы.
3. **Sensor:** в отдельной тестовой версии временно вставить `vTaskDelay(pdMS_TO_TICKS(4000))` сразу после получения запроса в `sensor_task`. При работающих UART и Idle ожидается `Deadline exceeded: sensor`, затем TWDT panic и перезапуск. Поздний ответ Sensor не отменяет сброс.
4. **Display:** аналогичная задержка после получения запроса в `display_task` должна дать `Deadline exceeded: display`, даже если Sensor продолжает отвечать.
5. **Flash/startup:** задержка 6000 мс после получения первого FLASH_SCAN должна обнаруживаться, несмотря на состояние `loaded=false`. Отдельно проверить задержку между шагами FLASH_READ/FLASH_ERASE: работа Sensor не маскирует зависание Flash.
6. **Длительная работа Flash:** штатные `read 0 256`, `flush` и `erase` на тестовом архиве не должны вызывать WDT, пока операции продвигаются. `erase` удаляет архив, поэтому этот сценарий выполнять только после сохранения нужных данных.
7. **UART:** задержка 4000 мс перед `pump()` в основном цикле должна привести к `Deadline exceeded: uart`, даже при отсутствии входящих команд.
8. **Подготовка сна:** в тестовой версии не отправлять EVENT_UART_PAUSED, оставив основной цикл UART работающим. После истечения сеанса UART ожидается `Deadline exceeded: sleep_handshake`; живой UART не должен маскировать отсутствие подтверждения.
9. **Manager:** задержка 6000 мс в начале его цикла должна вызвать непосредственно Task WDT; предварительного сообщения о прикладном канале может не быть.
10. **Восстановление:** после перезапуска проверить сообщение `(Task WDT)` в UART0, отображение ARCHIVE и чтение ранее сохранённых записей. Автоматического стирания нет. Новые измерения продолжаются после удаления тестовой задержки.

Тестовые задержки добавлять по одному сценарию и убирать после проверки; оставленная задержка будет повторять перезапуски. В рабочей версии нет команды, специально вызывающей зависание.

## Границы восстановления

WDT перезапускает устройство, но не сохраняет RAM-буфер и не исправляет физически неисправный датчик. Аварийная запись flash перед panic не выполняется. Используется прежний формат журнала: занятые сектора при старте не перезаписываются, частично сохранённый сектор пропускается для дальнейшего добавления; отсутствие CRC ограничивает обнаружение повреждений. Эти свойства требуют отдельной проверки на оборудовании.
