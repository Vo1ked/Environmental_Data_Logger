# WDT і panic

Застосунок використовує Task Watchdog ESP-IDF. Окрема задача для обслуговування WDT не створюється: зареєстрований Manager перевіряє незалежні строки роботи модулів. Реалізація: `main/watchdog/watchdog.c`; інтеграція — `main/manager/manager.c`, `main/storage/flash_log.c`, `main/uart/uart_task.c` та `main/main.c`.

## Строки та умови

| Канал | Початок контролю | Строк | Підтвердження роботи |
| --- | --- | --- | --- |
| Manager / TWDT | До стартових повідомлень задачам | 5 с без скидання лічильника TWDT | Перевірка всіх каналів без прострочень |
| Sensor | Перед SENSOR_SAMPLE або SENSOR_SET_TIME | 3 с | Manager отримав відповідь, зокрема з помилкою пристрою |
| Flash Writer | Перед будь-яким запитом, включно з початковим FLASH_SCAN | 5 с без поступу виконання | Оброблений блок сканування, успішне читання/запис/стирання; остаточно — відповідь Manager |
| Display | Перед надсиланням знімка стану на OLED | 3 с | Manager отримав відповідь, зокрема з помилкою OLED |
| UART | До запуску задач і перед resume | 3 с без виконання циклу | Повернення з обслуговування UART; наявність вхідних байтів не потрібна |
| Підготовка сну | Перед UART_PREPARE_SLEEP | 3 с | Manager отримав EVENT_UART_PAUSED: підтвердження або відмову |

Прикладні строки визначені в `main/app_config.h`, таймаут TWDT — у `CONFIG_ESP_TASK_WDT_TIMEOUT_S`. Це різні інтервали: після зависання Sensor спочатку спливають 3 секунди на відповідь, далі Manager припиняє скидати лічильник TWDT, і приблизно протягом наступних 5 секунд активної роботи відбувається panic/reset. Для Flash сумарний час становить приблизно до 10 секунд від останнього поступу. Зависання самого Manager контролюється безпосередньо TWDT.

Строки відлічуються за монотонним `esp_timer`, тому зміна RTC не впливає на них. Спільні поля захищені короткими критичними секціями для двох ядер. Прострочення перевіряється також під час завершення, продовження та повторного відкриття каналу. Запізніла подія не скасовує зафіксованої помилки; поступ Flash не продовжує строк Sensor.

Очікування задачі в порожній черзі не вважається активною операцією. Контроль починається **до** розміщення запиту в черзі; невдале надсилання скасовує його. Завершений запит із помилкою BME280, RTC, OLED або flash не вважається зависанням.

Manager додає текст до черги UART без очікування вільного місця. Переповнення вихідної черги може спричинити втрату частини діагностики або відповідей; запит слід повторити після завершення поточного виведення. Flash обмежено очікує чергу під час `read` і повертає помилку, якщо запис не вдалося передати.

Після виявлення прострочення Manager виводить `Deadline exceeded: <channel>` через USB Serial/JTAG, припиняє обслуговувати TWDT і очікує перезапуску, викликаючи `vTaskDelay`. Idle-задачі залишаються працездатними. Нові запити та Light Sleep не запускаються; уже прийняті операції можуть завершитися. Діагностика не залежить від logger або прикладного UART0.

## Налаштування panic

У `sdkconfig` і `sdkconfig.defaults` увімкнено:

```text
CONFIG_ESP_TASK_WDT_EN=y
CONFIG_ESP_TASK_WDT_INIT=y
CONFIG_ESP_TASK_WDT_TIMEOUT_S=5
CONFIG_ESP_TASK_WDT_CHECK_IDLE_TASK_CPU0=y
CONFIG_ESP_TASK_WDT_CHECK_IDLE_TASK_CPU1=y
CONFIG_ESP_TASK_WDT_PANIC=y
CONFIG_ESP_SYSTEM_PANIC_PRINT_REBOOT=y
CONFIG_ESP_SYSTEM_PANIC_REBOOT_DELAY_SECONDS=0
```

Під час запуску застосунок викликає `esp_task_wdt_reconfigure()` для автоматично ініціалізованого TWDT. Якщо ініціалізації ще не було, використовується `esp_task_wdt_init()`. Установлюються `trigger_panic=true` і контроль Idle-задач усіх активних ядер, після чого реєструється Manager. Помилки налаштування не ігноруються. Системний Interrupt WDT залишається ввімкненим.

Поведінку TWDT і panic описано в [документації Espressif](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-reference/system/wdts.html).

## Light Sleep

До сну мають завершитися Sensor, Display і Flash, пройти logger_flush та підтвердження паузи UART. Очікування підтвердження має окремий строк. Лише після позитивної відповіді UART його періодичний контроль призупиняється. Перед resume він запускається знову, включно з відмовою від сну або помилкою `esp_light_sleep_start()`.

Manager залишається зареєстрованим у TWDT. Застосунок не вимикає апаратні watchdog перед сном; на рівні периферії ними керує ESP-IDF. Один сон обмежений `APP_MAX_SLEEP_MS=1000`; статична перевірка вимагає запасу відносно таймауту TWDT. Активні операції завершуються до сну, тому він не витрачає їхні програмні строки. Повторні переходи сон/пробудження потрібно перевірити на платі.

## Перевірка на платі

Підготувати кілька збережених записів через `flush`. RAM-буфер втрачається під час перезапуску. Перевіряти WDT без OpenOCD/JTAG: налагоджувач може вимикати watchdog.

1. **Штатна робота:** перевірити `status` (WDT=ON, timeout=5 s, panic=ON), кілька хвилин вимірювань, відсутність команд, Light Sleep і пробудження через UART. Перезапусків бути не повинно.
2. **Помилки пристроїв:** запуск без BME280, RTC або OLED має давати повідомлення про помилки без WDT reset, поки задачі відповідають.
3. **Sensor:** у тестовій версії додати `vTaskDelay(pdMS_TO_TICKS(4000))` одразу після отримання запиту в `sensor_task`. Очікується `Deadline exceeded: sensor`, потім TWDT panic і перезапуск. Запізніла відповідь не скасовує скидання.
4. **Display:** така сама затримка після отримання запиту в `display_task` має дати `Deadline exceeded: display`, навіть коли Sensor відповідає.
5. **Flash/startup:** затримка 6000 мс після першого FLASH_SCAN має виявлятися навіть за `loaded=false`. Окремо перевірити затримку між кроками FLASH_READ/FLASH_ERASE: робота Sensor не маскує зависання Flash.
6. **Тривалі операції Flash:** `read 0 256`, `flush` та `erase` не повинні викликати WDT, поки виконання просувається. `erase` видаляє архів; потрібні дані слід зберегти перед перевіркою.
7. **UART:** затримка 4000 мс перед `pump()` має дати `Deadline exceeded: uart`, навіть без вхідних команд.
8. **Підготовка сну:** у тестовій версії не надсилати EVENT_UART_PAUSED, залишивши цикл UART активним. Після завершення сеансу очікується `Deadline exceeded: sleep_handshake`.
9. **Manager:** затримка 6000 мс на початку його циклу має викликати безпосередньо Task WDT. Попереднього повідомлення про прикладний канал може не бути.
10. **Відновлення:** після перезапуску перевірити `(Task WDT)` у консолі USB Serial/JTAG, позначку ARCHIVE та читання збережених записів. Автоматичного стирання всього архіву немає; після видалення тестової затримки вимірювання продовжуються.

Тестові затримки додавати по одному сценарію та видаляти після перевірки; залишена затримка повторюватиме перезапуски. Робоча версія не має команди навмисного зависання.

## Межі відновлення

WDT перезапускає пристрій, але не зберігає RAM-буфер і не виправляє фізично несправний датчик. Аварійний запис flash перед panic не виконується. Архів v2 перевіряє CRC32 та пропускає пошкоджені записи. Ротація звільняє весь застарілий день. Формат і відновлення описані у [storage.md](storage.md).
